# Scenario Lab V4 - Implementation Planning Brief

## Context

You are being asked to create a detailed implementation plan for **Scenario Lab V4**, a Python-based orchestration system for LLM-driven scenario simulations.

This document provides you with all the context you need. Please read it carefully before creating your plan.

## Project Background

### What is Scenario Lab?

Scenario Lab is a framework for running multi-turn simulations of complex scenarios using Large Language Models. Example use cases:
- Policy analysis: "How does Sweden handle AI development 2026-2030?"
- Geopolitical scenarios: "US-China AI race dynamics"
- Organizational strategy: "How do different stakeholders respond to disruption?"

### Evolution: V3 → V4

**V3 (archived)** was a complex hybrid system:
- Communication phases with action points
- Hybrid LLM + Python validation
- Relationship tracking, fact ledgers, information asymmetry
- 2000+ lines of Python orchestration code

**V3's key learning:** LLMs are better at handling complexity than we initially thought.

**V4 (what we're building)** radically simplifies:
- Pure LLM-driven: no game logic in Python
- Simple turn loop: Events → Actors → Metric Rules → Metrics Update
- Python only for: loading files, calling APIs, saving results
- Focus on prompt engineering, not code complexity

## V4 Architecture Overview

### Turn Structure

Each turn represents a time period (e.g., 6 months) and consists of four sequential LLM calls:

```
1. Exogenous Events
   Input:  Current metrics, world state, list of possible events
   Output: JSON array of events that occurred this turn

2. Actor Actions (parallel for each actor)
   Input:  Current metrics, world state, actor background
   Output: Actor's updated goals and narrative description of actions

3. Metric Rules Update
   Input:  Previous rules, current world state, actor actions
   Output: Updated list of quantitative rules governing metrics

4. Metrics Update
   Input:  Current metrics, metric rules, actor actions, events
   Output: Updated metrics (JSON) + narrative summary (markdown)
```

### Key Concepts

**Metrics**
- Quantitative state variables (pure numbers)
- Examples: `ai_capability: 6`, `unemployment: 7`, `public_sentiment: 1`
- Stored with metadata: min, max, unit, description

**Metric Rules**
- Quantitative relationships describing how metrics change
- Examples:
  - "ai_capability doubles every 6 months (from 3 at start)"
  - "When unemployment > 10, public_sentiment decreases by 1 per turn"
- LLM can modify these rules based on world changes

**World State**
- Narrative description of what happened during the turn
- Generated by LLM in step 4
- Serves as context for actors in the next turn

**Actors**
- Stakeholders in the scenario (governments, organizations, groups)
- Have background descriptions and goals
- Decide actions each turn based on world state

**External Events**
- Exogenous happenings with probabilities and conditions
- Examples: "AI breakthrough (5% chance)", "Election (100% when date matches)"

### Information Flow

```
Turn N begins with:
├── World State (narrative from previous turn)
├── Metrics (numbers from previous turn)
└── Metric Rules (from previous turn)

Turn N executes:
1. Events LLM call → which events occurred
2. Actor LLM calls → what each actor does
3. Rules LLM call → updated metric rules
4. Metrics LLM call → new metrics + new world state

Turn N+1 begins with:
├── New World State (from step 4)
├── New Metrics (from step 4)
└── Updated Metric Rules (from step 3)
```

## Prompt System

We have four system prompts (templates) in `docs/V4/prompts/`:

1. **01 - Exogenous events.md** - Events determination
2. **02 - Actor.md** - Actor decision-making
3. **03 - Metrics Rules Update.md** - Rule updates

### User Prompts (Turn-Specific)

For each turn, we construct user prompts by combining:
- Current metrics (JSON)
- Current world state (markdown narrative)
- Metric rules (numbered list)
- Actor background (from scenario files)
- Events list (from scenario files)

Example frozen prompts available in `docs/V4/early-testing/frozen prompts/turn1/`.

## Scenario Structure

A scenario is a directory containing:

```
scenario-name/
├── scenario.yaml          # Configuration
├── metrics.yaml           # Metric definitions
├── events.yaml            # External events
├── methods.py             # (Optional, for future extensions)
└── background/
    ├── context.md         # World background
    └── actors/
        ├── Actor1.md      # Actor descriptions
        └── Actor2.md
```

### scenario.yaml

```yaml
name: "Sweden AI 2030"
description: "AI policy scenario for Sweden 2026-2030"
time_scale: "6 months per turn"
start_date: "2026-01"
max_turns: 10
actors:
  - government
  - labor-unions
  - business-sector
  - media
```

### metrics.yaml

```yaml
metrics:
  - id: ai_capability
    description: "Hours of software dev work AI can handle (50% success)"
    min: 0
    max: 1000
    unit: "hours"
    start_value: 3
  - id: unemployment
    description: "Unemployment rate in Sweden"
    min: 0
    max: 100
    unit: "percent"
    start_value: 8
```

### events.yaml

```yaml
events:
  - id: ai_incident_sweden
    description: "Teen suicide after AI companion use - major media coverage"
    probability: 0.10
    condition: "ai_adoption_sweden > 30"
    can_repeat: true
  - id: general_election_2026
    description: "Swedish national election"
    probability: 1.0
    condition: "September 2026 in turn period"
    can_repeat: false
```

## LLM Integration

### Provider
- Use OpenRouter as primary LLM provider
- API endpoint: `https://openrouter.ai/api/v1/chat/completions`
- API key from environment: `OPENROUTER_API_KEY`
- Model configurable per scenario (default: `anthropic/claude-sonnet-4`)

### Request Format
```python
{
    "model": "anthropic/claude-sonnet-4",
    "messages": [
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": user_prompt}
    ],
    "temperature": 0.7  # configurable
}
```

### Response Handling
- Parse JSON from responses (steps 1, 4)
- Parse Markdown from responses (steps 2, 3, 4)
- Save raw LLM input/output for debugging
- Handle API errors gracefully
