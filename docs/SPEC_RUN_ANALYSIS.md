# Spec: Automatic Run Analysis

## Problem

Scenario Lab produces rich, inspectable artifacts for every turn. But the step from raw artifacts to insight is entirely manual. A user who completes a 10-turn run gets 80+ files and must read through events, narratives, metrics, and rule changes to understand what happened and why.

This is the weakest link in the current workflow. The orchestration engine is robust, persistence is thorough, and comparison tools exist – but the user still has to synthesize everything themselves.

## Goal

Add an `analyze` command that reads a completed run's artifacts and produces a structured analysis report. The report should answer the questions a user actually has after a run:

- What happened?
- What were the turning points?
- What drove the outcome?
- Were there surprising events or shifts?

## CLI Interface

```bash
python -m scenario_lab.cli analyze <run-dir>
python -m scenario_lab.cli analyze <run-dir> --model <model>
python -m scenario_lab.cli analyze <run-dir> --output analysis.md
python -m scenario_lab.cli analyze <run-dir> --json
```

### Arguments

- `<run-dir>` – Path to a completed run directory (e.g. `scenarios/sweden-ai-2030/runs/run-20260304-200354`).

### Options

- `--model <model>` – Override the LLM used for analysis. Defaults to the scenario's `summary` model. Should be a capable model since analysis requires synthesis across many artifacts.
- `--output <path>` – Write report to a custom path instead of the default location.
- `--json` – Output structured JSON instead of Markdown (for programmatic use).
- `--no-save` – Print to stdout only, do not save to disk.

### Default behavior

- Saves `analysis.md` (or `analysis.json`) inside the run directory.
- Prints a short summary to stdout.

## Report Structure

The analysis report should contain the following sections. All content is generated by a single LLM call that receives the full run context.

### 1. Summary (3–5 sentences)

A concise narrative of what happened across the entire run. Should read as a standalone paragraph that captures the outcome and its main drivers.

### 2. Key Metrics Overview

A table showing each metric's start value, end value, direction, and magnitude of change. Highlight metrics that changed dramatically or unexpectedly.

### 3. Turning Points

Identify the 2–4 turns where the simulation's trajectory shifted most significantly. For each turning point:

- Which turn and what time period.
- What happened (event, actor action, rule change).
- How it affected metrics and narrative direction.
- Why it mattered for the overall outcome.

### 4. Event Analysis

- Which events triggered and when.
- Which defined events never triggered and why (conditions not met, low probability).
- Whether triggered events had the impact their design suggested.

### 5. Actor Behavior Patterns

For each actor: a brief characterization of their strategy across the run. Did they adapt? Were they reactive or proactive? Did any actor's behavior dominate the outcome?

### 6. Rule Evolution

Summary of how metric rules changed over the run. Highlight rules that were added, removed, or significantly modified, and whether those changes were well-grounded in narrative events.

### 7. Constitutional Interventions (if applicable)

If the scenario has a constitution: which turns triggered referee corrections, what violations were found, and whether the corrections were appropriate.

### 8. Observations and Caveats

Potential issues the analyst (LLM) noticed:

- Metrics that seem unrealistic or poorly calibrated.
- Events that should have triggered but didn't (or vice versa).
- Narrative inconsistencies across turns.
- Potential improvements to the scenario design.

## Implementation

### Module: `scenario_lab/analysis.py`

New module. Responsible for:

1. Loading all artifacts from a completed run.
2. Building an analysis prompt.
3. Calling the LLM.
4. Parsing and saving the report.

### Data Loading

Read the following from the run directory:

| Source | What it provides |
|--------|-----------------|
| `config.json` | Scenario name, model config, turn count |
| `summary.json` | Per-turn metrics, occurred events, status |
| `costs.json` | Cost breakdown (optional, for report metadata) |
| `turn-XX/1-events.json` | Event evaluations per turn |
| `turn-XX/2-actors/*.md` | Actor actions per turn |
| `turn-XX/3-metric-rules.md` | Rule state and changelog per turn |
| `turn-XX/4-world-state.md` | Narrative per turn |
| `turn-XX/4-metrics.json` | Metric values per turn |
| `turn-XX/5-constitutional-check.json` | Referee results (if present) |
| `turn-XX/5-notepad.md` | Game master notes per turn |

Also load the scenario definition files (`metrics.md`, `events.md`, `constitution.md`) to give the LLM context about what was intended.

### Prompt Design

Use a Jinja2 template following the existing pattern:

- `templates/system-prompts/analysis.j2` – System prompt establishing the analyst role.
- `templates/user-prompts/analysis.j2` – User prompt with all artifacts injected.

The prompt should instruct the LLM to act as an analyst reviewing a completed simulation, not as a participant. It should reference specific turn numbers, metric values, and event names – not speak in generalities.

Allow scenario-level prompt overrides in `scenarios/<name>/system-prompts/analysis.j2` and `scenarios/<name>/user-prompts/analysis.j2`, following the existing template override pattern.

### Context Window Considerations

A 10-turn run with 5 actors produces substantial text. The implementation must handle this:

- **Primary approach:** Include all artifacts in a single prompt. Most modern models (128k+ context) can handle 10-turn runs comfortably.
- **Fallback for long runs:** If the total token estimate exceeds a threshold (e.g. 80k tokens), use a two-pass approach:
  1. First pass: Summarize each turn's artifacts into a condensed per-turn digest.
  2. Second pass: Analyze the digests.
- **Configuration:** Add `llm.max_tokens_by_task.analysis` for per-scenario token budget control.

### Output Format

**Markdown (default):** Sections use `##` headers. Metric tables use standard Markdown tables. Turning points use numbered subsections.

**JSON (`--json`):** Structured object with keys matching the report sections. Metric overview as array of objects. Turning points as array with `turn`, `description`, `impact` fields. This enables programmatic comparison of analyses across runs.

### LLM Task Registration

Register `analysis` as a new task in the LLM config system alongside `events`, `actors`, `rules`, `metrics`, `summary`, and `referee`. This allows per-scenario model selection for analysis, following the existing pattern.

Default model: same as `summary` task (since analysis is similar in nature – synthesis and writing).

## Integration with Existing Features

### `batch-run` integration (future)

Not in initial scope, but the design should allow a future `--analyze` flag on `batch-run` that automatically generates analysis for each completed run.

### `compare-runs` integration (future)

A natural extension would be to compare two `analysis.json` files programmatically, or to generate a comparative analysis from two runs in a single LLM call. Not in initial scope.

### Post-run hook (future)

Once analysis works well, it could optionally run automatically at the end of every simulation. Not in initial scope – keep it as an explicit command first.

## Testing

### Unit tests

- Test artifact loading from a fixture run directory.
- Test prompt construction with known inputs.
- Test Markdown and JSON output parsing.
- Test fallback behavior when optional files are missing (e.g. no constitution, no costs).

### Integration test

- Use a minimal fixture run (2–3 turns, 2 actors) with pre-written artifacts.
- Mock the LLM response.
- Verify the full pipeline from CLI invocation to saved `analysis.md`.

### Manual validation

- Run `analyze` on existing saved runs in `scenarios/sweden-ai-2030/runs/` and `scenarios/ai-safety-race/runs/`.
- Verify that turning points, event analysis, and metric observations match what a human reader would identify.

## Scope Boundaries

**In scope:**

- Single-run analysis from saved artifacts.
- Markdown and JSON output formats.
- CLI command with model override.
- Template-based prompts with scenario-level overrides.

**Out of scope (for now):**

- Multi-run comparative analysis.
- Automatic post-run execution.
- Visualization or charts.
- Interactive follow-up questions about the run.
